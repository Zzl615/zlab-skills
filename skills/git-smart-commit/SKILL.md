# Git Smart Commit

分析 git 变更，按**功能**（而非文件）归组，生成符合 Angular 规范的中文提交信息，并在用户确认后依次执行。

## 两种工作模式

根据当前情境选择对应模式：

### 模式 A：对话任务模式
**适用场景**：本次对话中 Claude 刚完成了代码修改任务（你已知道做了什么、为什么做）。

流程：
1. 运行 `git diff HEAD`，获取变更文件列表
2. 结合对话中完成的任务来理解改动意图，按功能逻辑分组
3. 生成提交信息（你的上下文理解优于纯 diff 分析，充分利用它）

### 模式 B：纯 git 分析模式
**适用场景**：用户完成了手动修改，对话中没有足够上下文。

流程：
1. 运行 `git diff --cached`；若暂存区为空则运行 `git diff HEAD`
2. 深入阅读 diff 内容，理解每处改动的意图（不要只看文件名）
3. 按功能逻辑分组

## 功能分组原则

- 同一个功能的多个文件 → 一个 commit
- 独立功能、独立 bug fix、文档更新 → 各自独立的 commit
- 判断依据是**改动目的**，不是文件路径或文件数量

## 输出格式

```
[1] feat(auth): 添加用户 JWT 登录认证
    涉及文件：src/auth/login.ts, src/middleware/jwt.ts

[2] fix(api): 修复用户列表接口分页错误
    涉及文件：src/api/users.ts

[3] docs(readme): 更新部署说明文档
    涉及文件：README.md
```

## Angular 规范

格式：`<type>(<scope>): <subject>`

| type | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档变更 |
| `style` | 格式调整（不影响逻辑） |
| `refactor` | 重构 |
| `test` | 测试相关 |
| `chore` | 构建/依赖/配置 |

**写法要求：**
- subject 用中文，动词开头（"添加"、"修复"、"更新"、"重构"）
- scope 用英文小写，代表模块名
- 简洁准确，不超过 50 字

## 确认与执行

展示完提交列表后，询问用户：

> "是否执行上述提交？输入序号选择部分（如 `1 3`），输入 `all` 全部提交，输入 `no` 取消。"

用户确认后，按序依次执行：
1. `git add <该 commit 涉及的文件>`
2. `git commit -m "<提交信息>"`
3. 全部完成后输出总结

## 边界处理

- **无任何变更**：提示"当前没有检测到 git 变更"，停止执行
- **已有暂存文件**：优先处理暂存区；若工作区还有未暂存变更，询问用户是否一并处理
- **变更范围很大**：识别主要功能模块，合理合并，避免拆分过细（5个以内 commit 为宜）
